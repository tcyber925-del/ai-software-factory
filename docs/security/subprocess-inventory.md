### Limitations
- **No execution/verification claims:** application workflows, agents, tests, typechecks, builds, linters, or runtime behaviors were **not** executed for this audit (except read-only git/grep/gh/filesystem inspection commands listed in §7). Subprocess behavior at runtime, OS process-tree semantics, signal delivery, and actual environment visibility to children are **not runtime-verified** here.
- **No containment claims:** Git worktrees are not treated as security sandboxes; filesystem/process/network containment was not tested or claimed.
- **No secret access:** no actual secret values were printed, copied, or recorded. Tests that reference env var names with synthetic values were not executed and no live credentials were encountered.
- **Search coverage limits:** primary pattern searches covered tracked `*.ts`, `*.tsx`, `*.js`, `*.mjs`, `*.cjs` via `git grep`. `git ls-files '*.sh' '*.py'` returned none. `scripts/` contains only `scripts/mutation/*.mjs` (confirmed by listing). Non-JS/TS executables, generated artifacts outside tracked source, or launch mechanisms not using the searched Node APIs/wrappers were not observed but cannot be proven absent without broader runtime instrumentation.
- **Host behavior assumptions avoided:** inheritance semantics noted below are based on Node.js API usage visible in source/options; actual host environment contents and OS-specific behavior are unverified.

## 4. Environment inheritance and credential-exposure findings

### Observed construction modes (source-level)
- **Explicitly constructed env (derived, non-allowlisted):** `scripts/mutation/evaluate.mjs:146-151` creates a child env from `process.env` minus `FORCE_COLOR`/`NO_COLOR`, plus `MUTATION_CORPUS=1` (SP-12). This is explicit in code but still broadly inherits ambient variables.
- **Implicit inheritance (no `env` specified):** SP-01, SP-02, SP-03, SP-04, SP-05, SP-06, SP-07, SP-08, SP-09, SP-10 (via SP-03), SP-11, SP-13 pass no `env` option. In Node.js, child processes inherit `process.env` by default when `env` is omitted (source-observed API usage; runtime not verified).
- **Allowlisted/minimized env:** **none observed** in production/runtime/verification/doctor/git/CLI launch paths.

### Credential/sensitive-data exposure paths (potential, evidence-limited)
- **Ambient secret inheritance:** any inherited-environment launch (especially SP-03 runtime agent execution, SP-04/SP-05 runtime CLIs, SP-06 verification commands, SP-11 npm/project scripts, SP-10 optional live probes, SP-12 mutation test runs) can expose credentials present in the parent process environment to child processes. Actual presence/values of credentials were not inspected.
- **Sensitive data in arguments:** Hermes/OpenCode/Herdr/runtime and probe invocations may carry task prompts or operational parameters in argv (SP-03/SP-04/SP-05/SP-10; exact argument contents depend on callers/runtime behavior). Command-line arguments can be visible to local process listings on some hosts (host behavior not tested).
- **Sensitive data in outputs/evidence:** verification stdout/stderr/exit evidence and event-log records (SP-06), CLI pass-through output (SP-11), and runtime evidence collection paths may capture tool output that could include secrets if emitted. Redaction behavior was not comprehensively verified in this audit.
- **Repository/config sources:** no subprocess launch site was observed reading secret files directly in source, but project-defined verification/npm scripts (SP-06 inputs, SP-11) and external runtimes/CLIs may access files or services using inherited credentials (unverified).

### Areas with no direct subprocess-based credential propagation observed
- Core kernel/pipeline/security modules inspected do not directly spawn subprocesses; they delegate to injected adapters/runners. GitHub/Linear intake and protocol validation paths were not identified as subprocess launchers in searched results.

## 5. Unverified behaviors and evidence gaps

- **Runtime execution semantics:** timeouts, signal handling, process-group termination, and zombie/orphan prevention were not exercised; only source-level options were reviewed.
- **Actual child environments:** real inherited variable sets, credential presence, and runtime/CLI behavior under those environments were not observed.
- **Process-tree behavior:** SP-03 implements group kill logic for detached POSIX processes in source; effectiveness across platforms/runtimes unverified. Other `execFile` sites (SP-01,02,04,05,06,07,08,09,11,13) do not implement custom tree-kill logic in source.
- **Output handling/redaction:** whether stdout/stderr/evidence/logs are truncated, sanitized, or excluded from persisted artifacts in all paths was not fully traced end-to-end at runtime.
- **Caller-provided command content:** exact verification commands (`ShellCheckSpec`), npm scripts executed by `factory verify`, and runtime-constructed CLI arguments/prompts for Herdr/Hermes/OpenCode depend on configuration/work units/external tools not executed here.
- **Coverage completeness:** absence of other launch mechanisms outside searched patterns/file types cannot be proven; dynamic `import()`-driven wrappers or future additions are out of scope.
- **Security policy alignment in dispatch:** issue #90/#92 context and current docs note separation between gate capability and dispatch wiring in some areas; this inventory does not reassess enforcement beyond subprocess/env evidence.

## 6. Prioritized follow-up questions for WU-92-02

1. **Environment minimization (highest):** Which subprocess paths must switch from inherited `process.env` to an explicit allowlist (or denylist for known secret classes), especially SP-03/04/05/06/10/11? What minimal variables are required per tool (PATH, HOME, locale, git/runtime-specific vars) without leaking credentials?
2. **Verification command boundary:** How should `ShellCheckSpec`/`factory verify` constrain or declare trusted commands and environments (SP-06, SP-11) given they can execute project/operator-defined actions with inherited secrets?
3. **Timeout and termination consistency:** Should SP-01/02/05/06/07/08/09/11/13 gain explicit timeouts and, where applicable, kill/process-tree handling consistent with SP-03/SP-04/SP-12 risk profiles?
4. **Prompt/argument sensitivity:** For SP-03/04/05/10, can sensitive task data be moved out of argv where supported, and what redaction/logging rules apply to command arguments and runtime evidence?
5. **Output/evidence redaction and size controls:** What guarantees are needed so verification/runtime/CLI outputs and persisted event evidence do not retain secrets or unbounded sensitive data?
6. **Optional live probes (`doctor --probe`, SP-10):** What additional safeguards (explicit confirmation, stricter env, network/credential posture, redaction) are required before use in sensitive environments, given #90 restrictions?
7. **Mutation/support scripts:** Should SP-12/SP-13 be treated as trusted dev-only tooling with documented env inheritance, or hardened similarly if run in CI with access to secrets?
8. **Dispatch/runtime integration:** How do subprocess/environment controls interact with planned credential/environment boundary work (#89/#92) and pre-dispatch/pre-agent security gates without weakening isolation or merge/verification gates?
